# 적용과 변경 관리

## 범위와 우선순위

이 규칙의 주 대상은 `custom_components/<domain>`이 있는 hass 리포입니다. 카드·Android·YAML 설정·애드온에는 문서·CI 보안·버전 관리 원칙만 적용하며 HA 통합 전용 검사를 강제하지 않습니다.

- **공식**: 링크한 HA/HACS/GitHub 규격. 사용 API와 배포 방식에 적용됩니다.
- **필수**: 이 표준을 채택하는 리포의 프로젝트 정책입니다.
- **권장**: 통합 특성에 맞게 채택합니다.
- 충돌 시 사용자의 명시적 지시와 적용 가능한 공식 규격을 우선하고, 로컬 예외를 기록합니다.

## 채택

**GOV-01 필수**: `STANDARDS.md`에 참조한 표준 커밋 SHA, 적용 profile, 예외(ID·이유·영향·대안·승인 근거·담당자·재검토 조건)를 기록합니다. 예시는 templates/integration/STANDARDS.md입니다. 새 통합은 main의 규칙을 검토해 적용하고, 기존 통합은 결함을 숨기지 않은 채 단계적으로 이관합니다.

**GOV-02 필수**: 이 리포는 별도 태그·GitHub Release·SemVer 없이 main과 커밋 이력으로 관리합니다. 문서는 main에서 확인하며, 실제 채택 PR에서는 `git ls-remote https://github.com/eigger/hass-repo-standards.git refs/heads/main`으로 검토한 commit SHA를 확인해 STANDARDS.md에 기록합니다. 공통 workflow/action 호출은 그 SHA로 고정하여 중앙 변경이 모든 리포에 즉시 적용되지 않도록 합니다. 템플릿의 `@main`은 채택 시 SHA로 교체하는 예시입니다.

**GOV-03 필수**: 규칙 변경은 날짜와 변경 내용을 CHANGELOG에 기록합니다. 기존 채택 리포에 영향을 주는 변경은 영향·이관 방법을 설명하고 각 리포의 명시적 채택 PR로 반영합니다. 이 규칙 리포의 관리 방식과 개별 통합의 배포 버전·릴리스 정책은 별개입니다.

**GOV-04 필수**: 각 리포 적용 작업은 [중앙 현황표](adoption-status.md)를 시작·종료 및 차단·범위 변경 등 의미 있는 상태 변화 시 갱신합니다. 담당자/세션 식별자, 적용 내용, 기준 SHA·대상 커밋·체크리스트·CI·리뷰 근거, 남은 작업과 갱신일을 기록합니다. 상세 명령·버전·리뷰 결과는 체크리스트에 한 번 기록하고 현황표에는 요약과 링크를 남깁니다. 중앙 갱신 직전에 최신 main을 확인하고 자기 리포 행만 변경하며 다른 세션의 기록을 보존합니다. 접근·푸시가 불가능하면 실제 반영 결과를 과장하지 않고 미반영 사유와 반영할 내용을 보고합니다.

**GOV-05 필수**: 기본적으로 주 에이전트가 구현·리뷰·검증을 수행하고 변경 규모와 위험에 따라 위임합니다. 큰 구조 개편, HA 로딩·수명주기·액션 동작 또는 공용 CI 실행 로직 변경은 구현자가 아닌 별도 담당자의 독립 리뷰를 받습니다. 실행 동작에 영향이 없는 문구·배지·중앙 도구의 생성 결과만 바꾸는 작업은 자체 리뷰로 충분하며, 구현을 서브 에이전트에 맡기지 않았다는 이유만으로 예외를 만들지 않습니다. 리뷰 방식·선택 근거·대상 커밋·결과를 체크리스트에 기록하고 지적 수정 후 영향 있는 검사를 재실행합니다. 독립 리뷰가 필요한데 수행할 수 없으면 미검증으로 남기며 완료로 처리하지 않습니다. 위임 시 필요한 diff·규칙·증거만 전달하고 담당 파일·완료 조건을 정합니다. 같은 파일의 동시 수정과 검증 환경 혼용을 피하며, 별도 사이드바 채팅 생성·메시지 전송 권한으로 해석하지 않습니다.

## 세부 지시 없이 적용하는 절차

사용자는 해당 리포 세션에서 **“hass-repo-standards 공통 규칙 적용해줘”**라고 요청하고, 필요하면 중앙 checkout 경로나 리포 URL을 지정합니다. 에이전트는 중앙 [AGENTS.md](../AGENTS.md)와 README를 직접 읽고, 아래 이관 순서와 체크리스트에 따라 점검·구현·리뷰·검증·중앙 현황 갱신을 진행합니다. URL을 적는 것만으로 지침이 자동 상속되지는 않으므로 적용 작업에서 문서 내용을 실제로 읽어야 합니다.

중앙 AGENTS.md는 적용 작업의 실행 지침이며 통합에 상시 설치할 문서가 아닙니다. 중앙 파일이나 그 내용을 통합의 AGENTS.md로 복사·생성·추가하지 않고, 다른 파일명으로 에이전트 진입 지침을 설치하지도 않습니다. 사용자 별도 요청 없이는 재설치하지 않습니다. 기존 리포 고유 지침은 임의로 수정·삭제하지 않습니다. 적용 기록은 STANDARDS.md의 검토 SHA·예외와 ADOPTION_CHECKLIST.md의 해당 시점 검증 근거로 남기며, 다른 커밋의 PASS를 현재 변경의 검증 결과로 재사용하지 않습니다. 같은 대상 커밋·환경·명령의 실제 검증은 링크로 공유할 수 있으며, 지적 수정 후에는 영향 있는 검사를 다시 실행합니다.

기기·API·라이브러리의 차이는 실제 코드·manifest·테스트·공식 자료에서 확인해 판단합니다. 사용자 제한과 기존 변경을 보존하며, 다른 리포까지 자동으로 적용하지 않습니다. commit/push/PR은 사용자 지시와 해당 리포 정책을 따르고 태그·릴리스를 자동 생성하지 않습니다. hass-kibble과 hass-catprinter 파일럿의 구현 전환·독립 검증을 완료했습니다. 다른 통합은 별도 착수 전 자동 변경하지 않습니다.

## 필요한 문서와 검증 범위

첫 채택은 README·채택 절차·체크리스트와 적용되는 규칙 원문을 확인합니다. 후속 작업은 STANDARDS의 기준 SHA·예외·기존 검증 범위를 확인하고, 기준 변경분과 실제 수정에 관련된 규칙·사용 안내 절만 읽습니다. 같은 세션에서 이미 확인한 문서는 내용이나 기준 SHA가 바뀌지 않았다면 다시 읽을 필요가 없습니다. T1~T6 설계·작업지시서·과거 검증 기록은 중앙 도구 개발 배경이며 일반 통합 적용의 필수 읽기 목록이 아닙니다.

최초 전체 채택은 적용 대상 전체를 점검합니다. 후속 부분 변경은 영향 있는 검사와 리포 필수 CI를 실행하고, 이번에 확인한 항목·기존 기록·미검증을 구분합니다. 문서만 바뀌었다면 실제 HA 동작·의존성·지원 환경에 영향이 없는 근거를 기록하고 HA 환경을 중복 구축하지 않습니다. HA 동작이나 의존성이 바뀌면 실제 최소/current 및 해당 라이브러리 하한 검증을 유지합니다. 부분 변경의 검증만으로 전체 재채택 완료를 주장하지 않습니다.

## 이관 순서

1. 현재 CI를 읽기 전용으로 조사하고 기본 브랜치·지원 HA·테스트 환경을 확인합니다.
2. 기존 회귀 테스트를 보존하며 Core 대응 구현과 tests/components/<domain>/ 배치, 실제 HA fixture·entry 로딩 검증으로 전환할 계획을 기록합니다.
3. 의존성 선언·HA 테스트 환경을 정리한 뒤 Validate와 실제 HA 기반 Python CI로 전환합니다. 필요한 브라우저·최소 HA job은 유지합니다.
4. 의존성 업데이트 bot은 dry-run으로 기존 변화와 비교하고 전환합니다.
5. README 배지와 STANDARDS.md의 검토 SHA·예외, ADOPTION_CHECKLIST.md의 검증 근거를 작성하고, 해당하는 BLE 통합은 [Bluetooth 문서 작성 규칙](bluetooth-documentation.md)에 따라 영어·한국어 사용자용 설정·추천 기기 안내로 연결합니다. 개발·구현 가이드를 사용자 설정 안내로 연결하지 않습니다.
   imagespec 사용 통합은 [payload 작성 규칙](payload-documentation.md)에 따라 양언어 기기별 여섯 절과 실제 전체 액션 YAML을 작성·보존하고 중앙 metadata/scaffold·실제 HA/설치된 renderer 계약으로 current와 정확한 하한을 검증합니다. 공통 매뉴얼은 imagespec 원본으로 연결하며 지원하지 않는 기능을 새로 만들지 않습니다.
6. 실제 원격 CI를 통과한 뒤 required checks 이름을 저장소 설정에 반영합니다.

`needs`/job 이름 변경으로 branch protection이 영구 대기하지 않도록 채택 PR에서 확인합니다. 이 표준 자체는 저장소 설정을 자동 변경하지 않습니다.

## 적용 체크리스트

각 통합을 채택·재검토할 때 [체크리스트 사용법](checklist.md)과 [복사용 템플릿](../templates/integration/ADOPTION_CHECKLIST.md)을 사용합니다. 대상 리포에 `ADOPTION_CHECKLIST.md`로 복사하고 `STANDARDS.md`에서 연결합니다. 참조 규칙의 커밋과 점검한 대상 커밋, 실제 파일·CI 결과·버전 조합을 함께 기록합니다.

미확인·미적용 항목을 완료로 표시하지 않습니다. 예외는 GOV-01의 사유·담당자·재검토 조건을 기록하고, 해당 없음은 기능이 존재하지 않는 근거를 적습니다. 부분 이관과 전체 완료를 구분하며 실제 HA 테스트·최소 버전 검증이 남아 있으면 그 상태를 그대로 남깁니다. 체크리스트 작성 자체가 기존 통합이나 CI를 전환하지는 않습니다.

## 중앙 템플릿과 예외

**GOV-01 필수**의 예외 기록은 임의 변형 허가가 아닙니다. README 공통 영역·테스트 기본 파일·공용 CI는 검토 SHA의 중앙 템플릿을 의무 적용합니다. 적용이 어려우면 에이전트가 이유·영향·대안을 사용자에게 제시합니다. 여러 리포에 필요한 개선은 중앙 템플릿을 먼저 수정·검증한 뒤 적용하고, 특정 리포의 예외는 사용자의 명시적 승인을 받은 뒤 적용합니다. 승인 전에는 우회하거나 PASS로 표시하지 않습니다.

STANDARDS.md에는 규칙 ID, 대상 경로·허용 범위, 이유·영향·대안, 승인자·일자·실제 승인 근거 링크/세션 참조, 담당자와 재검토 조건을 기록합니다. 자동 검사 예외가 필요하면 `.hass-standards.json`의 `exceptions`에 같은 기록의 ID·rule·paths·reason·approved_by·approved_at·evidence를 연결합니다. 빈 값·미확인·스스로 작성한 승인 선언을 사용자 승인으로 간주하지 않습니다. 승인 범위보다 넓은 wildcard나 무관한 규칙 제외를 만들지 않습니다. CI는 이 기록을 검사·반영할 뿐, 승인을 요청하거나 기다리지 않습니다. 에이전트와 독립 리뷰가 실제 승인 근거와 적용 범위를 확인합니다.

중앙 템플릿이 변경되어도 다른 리포를 자동 수정하지 않습니다. 각 리포의 적용·재검토 요청에서 기록된 전체 SHA와 최신 중앙 기준을 비교하고 변경 영향·새 SHA를 기록합니다. 기존 승인 범위 내 적용은 재승인을 요구하지 않습니다. 새 기준과 충돌해 기존 승인으로 판단할 수 없을 때만 에이전트가 충돌 내용과 대안을 설명하고 사용자에게 확인합니다.
